## 3. Detailed Technical Analysis

### [HYG-01] Resolver Version Mismatch (P2)

- **Location:** `Cargo.toml:14`
- **Rule Violated:** Rust 2024 edition recommends `resolver = "3"` for correct feature resolution with edition-specific defaults.
- **Problematic Code:** `resolver = "2"`
- **Mechanistic Root Cause:** Resolver 2 is the 2021-era resolver. Resolver 3 aligns with edition 2024's stricter feature unification rules. While resolver 2 works today, it may silently diverge on feature resolution as dependencies update to edition 2024 defaults.
- **Remediation:** Change `resolver = "2"` to `resolver = "3"` in `[workspace]`. Verify `cargo check --workspace` still passes (no feature regressions).

### [HYG-02] Pre-HMAC Memory Allocation Bound (P3 — FIXED)

- **Location:** `src/ipc/server.rs:76`
- **Rule Violated:** P3 — Zero-cost allocation hygiene. Unbounded allocation before trust boundary.
- **Problematic Code:** `const MAX_LINE_LENGTH: usize = 33_554_432;` (32 MB, exceeding `max_bytes = 1 MB`)
- **Mechanistic Root Cause:** If an operator set `max_line_length` to its old 32 MB default while `max_bytes` remained 1 MB, a single JSON frame could allocate 32 MB before HMAC verification. At default `max_bytes`, the connection would be dropped first — so this was a configuration-ratio risk, not a default-vulnerable defect.
- **Remediated Implementation:**
  ```rust
  /// Upper bound on a single line (batch reports). Equals DEFAULT_MAX_CONNECTION_BYTES
  /// (1 MB) so a single JSON frame can never allocate beyond the per-connection
  /// budget before HMAC auth gates the frame. Prevents OOM-before-auth.
  const MAX_LINE_LENGTH: usize = DEFAULT_MAX_CONNECTION_BYTES; // 1 MB
  ```

### [HYG-03] Mutex Poison Cascade (P3 — Informational)

- **Location:** `crates/ramshield-detection/src/lib.rs:334-340`
- **Rule Violated:** P1-adjacent — mutex poisoning propagation
- **Problematic Code:**
  ```rust
  let mut handles = self.worker_handles.lock().unwrap_or_else(PoisonError::into_inner);
  ```
- **Mechanistic Root Cause:** The code already uses `unwrap_or_else(PoisonError::into_inner)` to recover from a poisoned mutex. The ponytail comment documents this. The `spawn` lines (347-348) use `.expect("spawn batch processor")` which is a legitimate panic point — thread spawn failure is unrecoverable.
- **Status:** Already mitigated. No code change needed.

### [HYG-04 / HYG-05] Len-Minus-One Expressions (P3 — Informational)

- **Locations:** `forecasting/src/lib.rs:531`, `enforcement/src/lib.rs:279`
- **Analysis:**
  - `forecasting:531`: `self.vals.len() - 1` is safe — the function returns `None` early when `len() < 10` (line 524). The clamp floor is `(self.vals.len() - 1) as f64`, never reached at `len() == 0`.
  - `enforcement:279`: `vec.len() - 1` follows `vec.push(ip)` (line 278), so vec is guaranteed non-empty.
- **Status:** Both are safe. No change needed.
