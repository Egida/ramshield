OPTIONAL OBSERVATIONS

- Minor: the in-place update would be strictly more defensive as `entry.1 = entry.1.max(closed_last)`. With current invariants the two are equivalent (LSNs are monotonic, so `closed_last` is always the larger), so this is a hardening suggestion only, not a defect.
- Minor (cosmetic, test comments only): the new test's prose says segment 1's last LSN is 4 and segment 2's true last LSN is 9; with the actual record/segment byte sizes the true values are larger (the writer's LSN after the 3 appends is 11, asserted). The assertions themselves (seeded 8, safe 9, file exists / old file gone) are correct and independent of the exact byte layout, so the test remains valid — the prose numbers are just imprecise.
- UNVERIFIED: the exact per-record byte size and where the 400-byte `seg_max_bytes` boundary falls for the seeded segment (record = 23-byte header + 64-byte payload, plus any segment file header) was not measured; the review reasons about the LSN boundary (seeded 8 < safe 9 <= true last), which holds under any of these layouts.
- UNVERIFIED: `segment_reports` entries for the newest segment are seeded even when the segment holds no records (`last_lsn == None` -> filtered out at wal.rs:175). An empty segment therefore has no entry and is skipped by retention (`else { continue; }`). This is pre-existing behaviour, unchanged by the fix, and the active segment is skipped anyway.
- Not blocking: the fix does not change the fact that a segment whose last LSN is at or above the safe LSN is retained until a later checkpoint advances the safe LSN. Growth is therefore bounded by the checkpoint cadence, which is the intended policy ("max_bytes is a target, not permission to destroy history no checkpoint covers").
